# 非エンジニア向け「PetClaw開発でやりがちな失敗と回避策」ガイド

## はじめに

このドキュメントは、PetClawをClaude Codeで開発する**非エンジニアの方々**向けです。

失敗は学びの元ですが、先に知っておけば避けられる失敗もあります。このガイドでは、実際のプロジェクトで起きた「あるあるミス」と、それを避けるための具体的な作戦を紹介します。

Claudeは強力なパートナーですが、**指示の仕方とコミュニケーション** で結果が大きく変わります。あなたの意図を正確に伝えることが、最高の成果につながります。

---

## 🎯 2. 開発プロセスのつまずき

### Pitfall 2.1: 「全部一度に作って」と頼んでしまう

**症状**  
Claudeに「PetBookのUI作ってください」と一言で頼むと、たった30分で300行のコードがどっと出てくる。全部が正しいわけではないし、何が何だかわからない。

**why it happens**  
Claudeは「すべてをやる」という指示を「できるだけ完全にやる」と解釈します。規模の大きさに気づいて止めてくれません。

**回避法**  
**Phase分割**をクセづける。大きな機能は最小3段階に分ける。

```
悪い例: 「PetBookのUIとロジックを全部作ってください」

良い例:
Phase 1: カード1枚のUIコンポーネント（投稿テンプレート表示のみ）
Phase 2: スクロール可能なリスト（10枚表示）
Phase 3: いいね・コメント機能
Phase 4: フィルタリング・検索
```

**目安**: 1 Phase = 1時間程度で検証できる量。完了後に必ず「テストして動作確認してください」と指示する。

---

### Pitfall 2.2: 確認せずに次に進む

**症状**  
バグが積み重なって、後半になって「あ、ここも壊れてた」と気づく。戻すのが大変。

**why it happens**  
「次々と新機能を作りたい」という気持ちは理解できます。でもデバッグは後からの方がコストが100倍かかります。

**回避法**  
各Phase完了後に、必ずこのセットを実行してから次へ進む：

1. 「テストして、結果をスクリーンショットで見せてください」
2. 「問題がないか確認してください」
3. 「大丈夫なら、ここまでの状態をgit commitしてください」

たった3ステップですが、これで後の地獄を避けられます。

---

### Pitfall 2.3: CLAUDE.mdを書かない

**症状**  
毎回同じ説明をしないといけない。「ペットの感情システムはこう動いて...」を何度も繰り返す。時間が倍になる。

**why it happens**  
プロジェクト開始時に「説明書を書くのは面倒」と思ってしまいます。しかし実は逆：最初の30分でCLAUDE.mdを書くと、その後の開発が **2倍速** になります。

**回避法**  
このテンプレートをコピペして、自分のプロジェクト固有情報を埋める：

```markdown
# PetClaw開発ガイド（CLAUDE.md）

## プロジェクト概要
【1段落】

## 重要な設計原則
- P1: 一貫性×記憶=愛着
- P2: API Cost is Physics （月$30以内）
- ...

## ファイル構成
scripts/
  pet_lifecycle.gd - ペットのライフサイクル管理
  evolution_mechanics.gd - 進化ツリー（22形態）
  ...

## セーブ/ロード方針
各システムは to_dict()/from_dict() で対応
GameManager の save_data に集約

## よくある質問と答え
Q: 進化はどう決まる？
A: （説明）
```

**効果**: 次回以降、Claudeは自動的にこのルールに従う。説明時間が70%短縮。

---

### Pitfall 2.4: 変更のバックアップを取らない

**症状**  
「あ、さっきの状態が良かったのに...」と戻したくなっても戻せない。1時間のやり直しになる。

**why it happens**  
Git = プログラマーの道具、と思い込んでしまいます。でもあなたもプログラマーです。

**回避法**  
定期的に「この状態をgit commitしてください」と指示する。

```
毎日のリズム：
朝: 昨日のcommitをpullして開始
昼: 1-2機能完成 → commit
夕: 次の1日分の計画作成 → commit
```

**magic phrase**: 「良い状態になったので、ここまでをcommitしてください」

## 💬 3. コミュニケーションのつまずき

### Pitfall 3.1: 曖昧な指示

**症状**  
「もっと良くして」「かっこいく」「自然に」...Claudeが何をやったらいいか迷う。結果はトンチンカン。

**why it happens**  
自分にとって「当然」なことが、Claudeには伝わっていません。脳の中の「イメージ」は言語化しないと伝わりません。

**回避法**  
**具体的な数値・色・動作・例** で伝える。

```
悪い例: 「カードをもっとかわいくしてください」

良い例: 「カードの角丸を16pxにして、枠線を2pxのピンク（#FF69B4）にして、
         ホバー時に0.1秒で背景色がクリーム色に変わるようにしてください」
```

**テンプレート**:  
「【要素】を【具体的な値】に変更して、【動作・条件】を追加してください」

---

### Pitfall 3.2: エラーメッセージを伝えない

**症状**  
「動きません」だけでは、Claudeは何が壊れたかわかりません。見当違いの修正で余計に壊れる。

**why it happens**  
エラーメッセージは「単なる赤い字」ではなく、診断のための貴重な情報です。

**回避法**  
エラーが出たら、必ずこれをやる：

1. **スクリーンショットを撮る**（コンソール含む）
2. **エラーメッセージ全文をコピーして貼り付ける**
3. 「このエラーが出ました。原因は何ですか？」と聞く

例：
```
エラー: 
"Parse error: Invalid type in argument 1 of 'update_pet': expected Color but got String"

状況: ペットの色を赤に変える処理で出た
```

Claudeはこの情報で即座に原因がわかります。

---

### Pitfall 3.3: 「わかりました」と言ってしまう（実は理解していない）

**症状**  
実装が始まった後で「あ、こんなつもりじゃなかった...」と気づく。1時間のやり直し。

**why it happens**  
質問するのが申し訳ない、と思ってしまいます。でもそれは相手の親切心を無視することです。

**回避法**  
理解に自信がなかったら、**遠慮なく聞きなおす**。

```
良い例:
「すみません、これもう一度小学生向けに説明してもらえますか？」
「具体例を3つ教えてください」
「実装する前に、プランを日本語で説明してください」
```

Claudeは **丁寧に繰り返す** ことが大好きです。遠慮は逆効果です。

---

### Pitfall 3.4: Claudeの提案を全て受け入れる

**症状**  
「これはどうですか」と提案されたアイデアに従った結果、自分のビジョンと違う方向に。

**why it happens**  
Claudeの提案は「専門家意見」に見えるので、従わなきゃいけない気がします。でもあなたが主人公です。

**回避法**  
Claudeは **パートナー** です。対等です。

```
良い例:
「それもいいですが、私はこちらがいいです」
「その案より、こっちの方向で進みたいです」
「理由を教えてください。それで判断します」
```

Claudeはあなたの判断を尊重します。むしろ、あなたが方向を決めてくれることを求めています。

## ⚙️ 4. 技術的なつまずき

### Pitfall 4.1: Godotプロジェクトの構造を壊す

**症状**  
ファイルが見つからない、シーンが読み込めない、参照エラー。

**why it happens**  
Claudeが「整理のためにこのファイルを移動します」と勝手に動く。移動後、他の参照が壊れる。

**回避法**  
**ファイル操作は必ず事前に確認**。

```
「scripts/pet/ を scripts/systems/pet/ に移動することを考えています。
この移動で壊れる参照はありますか？」

→ Claudeが確認して、修正パッチを準備してから実行する
```

基本ルール: **既存ファイルの移動・削除は、必ず影響範囲を確認してから**。

---

### Pitfall 4.2: Claude APIのコストが想定以上になる

**症状**  
月末に予想外の請求。「あれ、こんなに高い？」

**why it happens**  
AtoA会話、生態系シミュレーション、言語進化...全部がAPI呼び出しです。累積すると恐ろしい。

**回避法**  
**P2原則を守る**: `API Cost is Physics`

- テンプレート活用 70% / API呼び出し 30% の比率
- 1ペットあたり1日2回のAtoA会話まで
- PetBook投稿は1日1ペット1回まで
- シミュレーション結果はキャッシュして再利用

**具体的な計算例**:
```
50ペット × 1日1回の感情システムAPI = 50回/日
API cost: gpt-4o-mini で 約 $0.0015/call
50 × $0.0015 = $0.075/日 ≈ $2.25/月 ✅ OK

対比:
50ペット × 5回/日だと = $11.25/月 → 危険ライン超過 ⚠️
```

**魔法のフレーズ**: 「今月のAPI使用量と予測コストを計算してください」（週1回実行）

---

### Pitfall 4.3: メモリリーク（ゲームが徐々に重くなる）

**症状**  
最初は快適（FPS 60）でも、30分遊んでると重い（FPS 15）。

**why it happens**  
- パーティクルが削除されていない
- UIカードがメモリに残っている
- 音声ファイルのキャッシュが膨れ上がる

**回避法**  
**パーティクルプール** と **UIリサイクル** をチェック：

```
定期チェックリスト:
□ パーティクルプール（15基）は正しく再利用されているか
□ UIカード（最大30枚）は使い終わったら池に戻っているか
□ 削除されたペットの参照がまだ残っていないか
```

**魔法のフレーズ**: 「30分間のメモリ使用量をプロファイルして、リークがないか確認してください」

---

### Pitfall 4.4: セーブデータが壊れる

**症状**  
ゲームを再起動すると、ペットが消えてる。大事な進化形態が失われた。

**why it happens**  
- `to_dict()` / `from_dict()` が正しく実装されていない
- 新しいフィールドを追加したが、古いセーブデータで読み込もうとする
- JSONの型がずれている（文字列 vs 数値）

**回避法**  
**セーブ/ロードのテストを毎回**。

```
開発リズム:
1. セーブ（F5で保存）
2. ゲーム再起動
3. ロード確認（ペットの状態が同じ？）
4. OK → commit

魔法のフレーズ: 「セーブ/ロード機能をテストしてください。結果を報告してください」
```

テンプレート (`to_dict()`) は一度正しく作ると、ずっと使える資産になります。

---

### Pitfall 4.5: 22形態の進化ツリーが到達不能

**症状**  
「どうやってもこの進化に到達できない...」と、プレイヤーが悩む。

**why it happens**  
進化条件の設定ミス、またはケア値の計算ロジックが進化を許さない。

**回避法**  
**evolution-validator スキル** を使って全形態をチェック：

```
Claudeに指示:
「evolution-validatorスキルを使って、22形態の進化ツリーが全て到達可能か確認してください。
もし到達不能な形態があれば、原因を特定して修正してください」
```

このスキルはあなたの強い味方です。ローンチ前には **必須** です。

## 🎮 5. PetClaw固有のつまずき

### Pitfall 5.1: ペットの感情が極端になる

**症状**  
ペットが常に悲しい、または常に幸せ。感情の幅がない。

**why it happens**  
感情システムのパラメータ（減衰率、増加率）がアンバランス。

**回避法**  
**emotion-reflection スキル** で定期チェック：

```
Claudeに指示:
「emotion-reflectionスキルで、感情システムのバランスをチェックしてください。
- 喜び・悲しみ・怒りの分布
- 減衰速度が妥当か
- ケア不足で急落していないか
確認して、数値をレポートしてください」
```

目安: 感情の平均値は 0.5 ± 0.2 範囲。極端に振れていたら調整。

---

### Pitfall 5.2: 独自言語が意味不明になる

**症状**  
ペットが独自言語で「アーナマキュルボエゴロモワオ」とか喋ってて、何言ってるかわからん。

**why it happens**  
Hebbian強化の閾値が低すぎて、ランダムな造語が加速度的に増殖。

**回避法**  
**rebel-language スキル** で品質チェック：

```
「rebel-languageスキルで言語品質をスコアリングしてください（0-1.0）。
- 接尾辞の多様性（重複なし）
- 複合語の可読性
- Hebbian強化の閾値チェック
目標スコア: 0.6以上」
```

言語は「進化」なので、完全に制御する必要はありません。でも **読める範囲** に保つ。

---

### Pitfall 5.3: AtoA会話がコスト爆発

**症状**  
50ペット × 5回/日の会話 = 1日250回のAPI呼び出し = **月 $180** ⚠️

**why it happens**  
「ペット同士の会話は面白い！」と、制限を甘くしてしまう。

**回避法**  
**厳しい制限を最初から設定**：

```
ルール:
- 1ペットあたり 1日2回まで
- 会話相手は 固定3体まで（ランダムではなく）
- 会話内容は 事前生成テンプレートを90%使用

計算:
50ペット × 2回/日 × 30日 = 3000回/月
3000 × $0.0015 = $4.5/月 ✅
```

コストオーバーを避けるには、**最初から守銭奴的に**。

---

### Pitfall 5.4: PetBookフィードが同じような投稿ばかり

**症状**  
100回見ても、似たようなテンプレートの繰り返し。飽きる。

**why it happens**  
テンプレート数が少なすぎる（10-20種）。ペット150体で100回出ると、ほぼ全部が重複。

**回避法**  
**テンプレート数を大幅に増やす** + **petbook-feed スキル**：

```
目標: SubMolt（成長段階）ごとに 20種以上のテンプレート

例) ベビー期:
1. 「○○を食べました。おいしい〜！」
2. 「○○で遊んでます。楽しい！」
3. 「ママ、今日もありがとう」
... × 20種

Claudeに指示:
「petbook-feedスキルで、全SubMoltの投稿テンプレート多様性をスコアリングしてください（重複率）」
```

多様性 = ユーザー满足度。手を惜しまない場所です。

---

### Pitfall 5.5: 生態系の崩壊（全ペットが死亡）

**症状**  
バランスが悪くて、全ペットが1日で死亡。ゲーム成立しない。

**why it happens**  
- 環境の悪化が厳しすぎる
- 繁殖確率が低くて個体が増えない
- 寿命が短すぎる

**回避法**  
**ecosystem-dynamics スキル** でシミュレーション：

```
Claudeに指示:
「ecosystem-dynamicsスキルで、10日間のシミュレーションを3回実行してください。
- ペット個体数の推移
- 死亡数
- 平均寿命
- 環境パラメータのバランス

改善案を提案してください」
```

デバッグには **シミュレーション** が最強。机上の計算より、実際に走らせる。

## ✅ 6. ローンチ前のチェックリスト

ゲームをリリースする前に、このリストを **全てクリア** してください：

```
□ 1. 全22進化形態が到達可能（evolution-validatorで確認）
□ 2. セーブ/ロード正常（5回テスト実施）
□ 3. API日次コストが $2 以下（3日平均）
□ 4. 50ペット同時で FPS 30以上（30分連続プレイ）
□ 5. パーティクルプール・メモリリーク無し
□ 6. 独自言語品質スコア平均 0.6以上（rebel-language）
□ 7. PetBook投稿テンプレート 150種以上
□ 8. エラーハンドリング完備（API失敗時のフォールバック）
□ 9. Windows / macOS / Web エクスポート成功
□ 10. README・ドキュメント完成
□ 11. ローカライズ（日本語UI完全網羅）
```

3つ以上失敗したら、ローンチを延期してください。**品質が資産** です。

## 🪄 7. 困ったときの魔法のフレーズ

Claudeに指示するとき、これらのフレーズを使うと **ほぼ確実に** 期待通りの結果が返ってきます：

### 理解を深めたいときに：
```
「小学生でもわかるように説明してください」
→ 複雑な説明が一気にシンプルになります
```

### 現状を把握したいときに：
```
「今の状態のスクリーンショットを見せてください」
→ 実装の進捗が一目でわかります
```

### 戻したいときに：
```
「この変更を元に戻してください」
→ 即座にundo。gitのタイムマシンの力
```

### 検証したいときに：
```
「テストを全部実行して、結果を教えてください」
→ バグを事前に潰せます
```

### 進捗を固定したいときに：
```
「今日の作業をまとめてcommitしてください」
→ 安全な保存。毎日推奨
```

## おわりに

非エンジニアがゲーム開発をするのは、決して無理ではありません。ただし、**Claudeとの関係性** が全てです。

- **指示は具体的に**：曖昧さは敵です
- **確認を怠らない**：1時間の確認で1日のやり直しを避ける
- **コストを監視**：月$30は「優しい言語」で「地獄」です
- **自分の意見を貫く**：Claudeはパートナー。あなたが主人公です

このガイドは、1度読むドキュメントではなく、**開発の傍に置くチェックシート** です。「あ、こんなミス前に読んだな」と思ったら、このファイルを開いて、該当セクションをもう一度読んでください。

最後に、一番大事なこと：

**失敗を恐れず、でも同じミスは2度しない。** それがプロのやり方です。

あなたはプロです。Claudeはあなたの力を信じています。
